## Shared Repository Role Contract

Every JSONWisdom repository follows the same discoverability rules.

Each repository must have a root `README.md` containing these fields near the top:

```yaml
repository: jsonwisdom/REPOSITORY_NAME
role: One sentence describing the repository's unique job.
system_layer: identity | operations | evidence | registry | verification | replay | publication | continuity | application | archive | experiment
authority: none | source | derived | presentation
truth_source: true | false
inputs:
  - upstream repository, record type, or external source
outputs:
  - artifact, receipt, registry record, application, or publication
canonical_for:
  - the exact responsibility this repository owns
not_canonical_for:
  - responsibilities explicitly owned elsewhere
status: active | experimental | placeholder | archived
replaced_by: null
```

Rules:

1. **No undocumented authority.** A repository without a declared role is not canonical merely because it exists.
2. **One unique job per repository.** Overlapping repositories must state their boundary and relationship.
3. **Receipts before claims.** Presentation, narration, or rendering cannot promote a claim into verified evidence.
4. **Inputs and outputs must be named.** Cross-repository flows must be traceable.
5. **Replacement must be explicit.** Versioned, forked, prototype, and successor repositories must identify predecessors and successors.
6. **Private stays private.** Private repository names and roles are not published through this public index without an explicit decision.
7. **The registry is evidence-based.** This page records README declarations and documentation gaps; it does not invent missing roles.
8. **The same checks apply to every repository.** No project is exempt because of age, size, naming, or perceived priority.

### Required GitHub Actions checks

A shared reusable workflow should enforce:

- root `README.md` exists;
- required role fields are present;
- `canonical_for` does not conflict with another active repository;
- predecessor/successor relationships resolve;
- referenced repositories and paths exist;
- placeholder and archive repositories cannot claim production authority;
- generated render layers identify their upstream truth source;
- this registry is regenerated when repository metadata changes.

Until those checks are installed account-wide, this registry should be treated as a documented inventory with known gaps—not a mechanically enforced control plane.

## Render Layer Notice

A render layer may be attached to `COMPUTERWISDOM`, `AL`, and `JOY` as a presentation surface for locked or clearly labeled records.

Allowed render posture:

```json
{
  "layer": "render",
  "truth_source": false,
  "authority": false,
  "rule": "receipts first, render second",
  "membrane": "HOLDS"
}
```

Render output may make records easier to read, share, export, or publish.

Render output must not silently promote:

```text
OBSERVATION -> CLAIM
CLAIM -> RECEIPT
RECEIPT -> VERIFIED_RECEIPT
UNKNOWN -> FACT
DISPUTED_RECORD -> RESOLVED_RECORD
```

Pretty output is not proof.
